# ISSUE-276: Research — Centralized Searchable Lists for Materials, Tags, Entities, Sounds, and Particles

## Context & User Story
- **Goal:** As a server admin, I want every editor control with a searchable recommended list (materials, tags, entities, sounds, particles) to draw from one exhaustive, centralized source, so the completeness and quality of the suggestions are consistent across the whole GUI instead of varying page by page.
- **Agent Role:** You are an expert frontend and backend architect producing a research report. This is a research ticket: deliver a development plan in a markdown report document for the maintainer to review. Do not implement production code.
- **Deliverable:** `docs/reports/REPORT_SEARCHABLE-LISTS.md`, written to the standards in `docs/AGENTS.md` (header states the owning ticket and date, cross-links to this ticket, ASD-STE100 prose).

## Research Goals
- [x] Inventory every searchable recommended list in the frontend and rate its completeness. Known starting points: `assets/materials.json` (used only by `MaterialPicker.vue`), `MATERIAL_SUGGESTIONS` + `TAG_SUGGESTIONS_BASE` in `SkillEditorPage.vue` (a second, divergent material list and a duplicated tag list also in `TagsPage.vue`), `SOUND_SUGGESTIONS` in `SoundConfigEditor.vue` (~59 of ~1,100 sound events), `PARTICLE_SUGGESTIONS` in `AbilitiesSection.vue`, and the absence of any entity-type list. Confirm whether any lists are duplicated and have already drifted.
- [x] Design a shared, centralized mechanism all controls reuse. Evaluate: a Pinia registry store modeled on the existing `stores/registries.ts` (fetch + `loaded` guard + offline fallback) that also serves materials/tags/entities/sounds/particles; shared constant modules for offline fallback (model on the existing fallback-constant pattern used by mechanics/triggers/state-filters, but with single copies instead of the current hand-duplicated fallbacks); and refactoring controls that hardcode their list internally (`MaterialPicker.vue` imports `materials.json` directly) to consume the shared source.
- [x] Decide the best source of the lists. Research and compare at least: (a) keeping lists hardcoded and manually maintained (today's state, cheapest, always drifts); (b) backend-served exhaustive lists enumerated from live Bukkit `Registry` objects (`Registry.MATERIAL`, `Registry.SOUND_EVENT`, `Registry.PARTICLE_TYPE`, `Registry.ENTITY_TYPE`, plus vanilla block/item/entity tags), noting the precedent that `Skilling.registerBuiltins()` already wires these registries and that `/api/mechanics`, `/api/triggers`, `/api/state-filters` already serve registry-derived data; (c) online sources, explicitly investigating whether the external-resource approach used for item textures (`MinecraftIcon.vue` fetching from `raw.githubusercontent.com/InventivetalentDev/minecraft-assets/{version}/...`) can also supply name lists (e.g. Mojang registry JSON, the same minecraft-assets repo, or a version-pinned registry dump), with caching, version pinning, and offline behavior considered.
- [x] Specify the recommended API shape if backend-served (e.g. `GET /api/materials`, `/api/sounds`, `/api/particles`, `/api/entities`, `/api/tags/all` for vanilla tags) and how each existing control (`AppCombobox`, `MaterialPicker`, `MaterialMultiSelect`, `FilterBuilder`, `SoundConfigEditor`, `AbilitiesSection`) would consume it.
- [x] Account for performance and version drift: how to cache lists, how often they change (per Paper/Minecraft version), and how a server on a different version than the lists stays correct.
- [x] Produce a phased development plan with a recommended approach, one alternative considered, and open questions for the maintainer to decide.
